Content Engine · ce

From a raw capture to a published post

Eleven stages, one project at a time. Filled circles are things only you can do — outlined circles are what the pipeline does for you once you've made a call. Every CLI command below has an equivalent screen in ce gui; the sequence is identical either way.

  1. 01
    Capture Manual
    ce capture audio|screen|friction <file|note>

    Record the raw material as it happens — audio notes, screenshots, one-line friction reports. Nothing downstream can invent what wasn't captured here.

    Tip

    Capture friction in the moment, not from memory later. "It just died, no warning" is a real quote from a real capture in this project — a reconstructed version a week later reads flat by comparison.

  2. 02
    Harvest Automated
    ce harvest <project> [--skip-research]

    Pulls git history, transcribes pending audio, runs a project-wide research pass, then drafts a batch of candidate briefs (briefs.yml).

    Tip

    Fill in project.yml#tags and #selection.demand_signals before this runs. Both feed straight into the brief-drafting prompt — an empty tags: [] gives the model nothing to search or angle against.

Known landmine — before you re-harvest

ce harvest fully rewrites and renumbers briefs.yml every time — it never merges. Every downstream command (produce, verify, assets, render, package, publish) resolves its piece's brief live, by id, from whatever briefs.yml currently holds.

Re-harvesting after you've already selected a brief can silently point an in-flight piece at a different brief's content, or break it outright. New captures always get picked up on the next harvest regardless — the risk is only for a piece already mid-pipeline. Finish or park it first.

  1. 03
    Review & select a brief Manual
    ce brief list <project> ce brief select <brief-id> [--skip-research]

    Weak or too-similar briefs are already disabled — the judgment call is which of what's left is worth writing. Selecting a brief promotes it to a piece and runs a second research pass scoped to this brief's own title and angle.

    Tip

    Read weakest_point before you pick. It's the system naming its own gap in the evidence — plan to address it (a caveat, more evidence) rather than let the article overclaim past what actually supports it.

  2. 04
    Produce Automated
    ce produce <piece-id> [--no-cache]

    Drafts the article, self-grades it against five weighted dimensions, and revises — up to a configured attempt limit or until the grade clears the bar.

    Tip

    The two reasoning-tier calls in this pipeline — brief_generate and article_grade — are consistently the priciest line items in a run's cost breakdown. Worth knowing before you re-run produce on a whim just to see a different draft.

  3. 05
    Edit the draft Manual
    $EDITOR article.md

    Open article.md and actually change it. This is the one step the whole system is built to assume happens — ADR-008's edit check (a later mtime vs. generated_at) exists purely to notice whether you did.

    Tip

    This is the single highest-leverage manual step for quality. A self-graded 8/10 draft is a first draft, not a final one — voice, specificity, and the honest caveat about the weakest point all improve here, not in the prompt.

  4. 06
    Verify Automated gate
    ce verify <piece-id> [--force]

    Extracts every factual claim, classifies it (grounded / external / opinion), and checks each one. Anything unverifiable blocks the pipeline unless you override it.

    Tip

    Read verification.json before reaching for --force. A blocked claim is almost always pointing at a real gap in the evidence, not a false positive.

  5. 07
    Stage assets Manual, required input
    assets/hero-source.<ext> assets/thumbnail-bg.<ext> assets/diagrams/*.mmd evidence/*

    Nothing here is generated from nothing. Drop a real screenshot, a code snippet, a hand-authored Mermaid diagram — whatever this piece actually has — into the piece's own folder before running ce assets.

    Tip

    Skip this and ce assets still "succeeds" — with a flat dark rectangle for a thumbnail and nothing else. It's a working renderer with an empty pantry, not a bug.

  6. 08
    Render assets & copy Automated
    ce assets <piece-id> [--only KIND] ce render <piece-id> [--platform P]

    Renders whatever was staged into PNGs, then adapts the article into per-platform copy for LinkedIn, Facebook, and YouTube — each with its own length limits and hook rules.

  7. 09
    Package & review Manual QA gate
    ce package <piece-id> → outbox/<id>/REVIEW.html

    Opens as one self-contained page: every platform's copy box with a live character counter, the staged images, a screenshot checklist. Read all of it before anything ships.

  8. 10
    Publish the site Automated, confirm-gated
    ce publish site <piece-id> [--dry-run]

    The one command in this whole pipeline that reaches outside the machine — a real git commit and push. It's the only stage the GUI puts behind an explicit confirm dialog.

  9. 11
    Post & track Manual, always
    ce metrics pull

    Copy each platform's rendition from REVIEW.html and post it yourself — there is no API auto-posting anywhere in this system, by design. Site clicks and YouTube stats pull back automatically later; LinkedIn and Facebook engagement numbers have no public API and stay hand-entered into posted.yml.

Two rules worth remembering

→ Never re-harvest a project with a piece still mid-pipeline without finishing or parking that piece first — see the landmine above stage 03.
→ The draft is not the article every stage from produce onward assumes you actually opened article.md and changed something — the grading loop measures a floor, not a ceiling.
